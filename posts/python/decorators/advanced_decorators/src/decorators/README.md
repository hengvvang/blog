# 类装饰器与元信息

在第一部分中，我们深入剖析了函数装饰器的闭包本质。然而，在设计复杂的工业级架构时，仅使用函数装饰器往往会面临**状态管理困难**、**难以进行面向对象扩展**以及**结构松散**等瓶颈。

为了解决这些局限性，Python 提供了强大的**类装饰器（Class-based Decorators）**。类装饰器允许我们利用类（Class）这一面向对象的核心工具，将装饰器的逻辑、配置属性及运行时状态封装在优雅的类实例中。

---

## 1. 为什么选择类装饰器？

相比于多层嵌套的函数装饰器，类装饰器在以下几个维度上展现出天然的工程优势：

* **直观的状态管理**：在函数装饰器中，若要维护调用计数、缓存结果或记录重试次数，我们必须依赖闭包变量及 `nonlocal` 关键字。而在类装饰器中，这些运行时状态可以直接作为实例属性（`self.state`）存储，清晰且易于维护。
* **清晰的参数化支持**：当装饰器需要接收复杂的配置参数时，函数装饰器需要写成三层嵌套的函数（外层接收参数，中层接收函数，内层定义 wrapper）。而类装饰器可以把接收参数和接收函数这两个职责分别拆分给 `__init__` 和 `__call__`，极大降低了代码的认知负载。
* **易于继承与重构**：作为一个类，它支持继承、多态及混入（Mixins），这使得我们能够设计出可扩展的“装饰器基类”，在不同的子类中复用公共前置/后置逻辑。

---

## 2. 元信息丢失防范与方法绑定失效

在享用类装饰器便利的同时，它也引入了两个极其致命的缺陷，必须引起系统工程师的高度关注：

### 2.1 装饰实例方法时的 `self` 绑定失效
这是 Python 描述符协议中最高频的 Bug 之一。当一个类装饰器用于修饰另一个类的实例方法时，因为类装饰器实例替代了原方法，而在默认情况下类实例没有实现描述符协议（即没有 `__get__` 方法），导致在通过外部实例调用该方法时，`self` 参数无法被正确注入，最终报 `TypeError`。

### 2.2 函数元信息的丢失
无论是函数装饰器还是类装饰器，被装饰后的函数名 `__name__` 和文档字符串 `__doc__` 都会被替换为包装器的相关信息。这不仅会使调试栈跟踪变得混乱，还会导致自动化文档工具（如 Sphinx）生成错误的文档，以及静态类型检查工具（MyPy/Pyright）无法推导正确的签名。
