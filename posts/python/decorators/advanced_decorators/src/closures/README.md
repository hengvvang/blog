# 作用域与闭包

在 Python 编程语言中，装饰器（Decorator）的设计与应用从根本上依赖于其底层的**闭包机制（Closure Mechanism）**与**词法作用域（Lexical Scoping）**。如果将装饰器视作上层建筑，那么闭包就是支撑该建筑的坚实地基。本部分将引导读者深入 Python 虚拟机的变量寻址与生命周期管理机制，拆解闭包的核心概念。

---

## 1. 词法作用域与作用域链

Python 采用的是**词法作用域（Lexical Scoping）**，这意味着变量的作用域是由代码在源文件中的物理位置决定的，而不是由运行时的调用栈决定的。

当我们在一个嵌套函数中查找某个变量时，Python 会沿着**作用域链**自内向外进行检索，这也就是经典的 **LEGB 规则**（Local -> Enclosing -> Global -> Built-in）。

* **L (Local, 局部作用域)**：当前函数或 lambda 表达式内部定义的变量。
* **E (Enclosing, 嵌套/外层作用域)**：包裹当前函数的外部函数（但非模块全局）的局部作用域。
* **G (Global, 全局作用域)**：模块级别定义的变量，即在文件顶层声明的变量。
* **B (Built-in, 内置作用域)**：由 Python 内置模块（`builtins`）提供的名称，如 `print`、`ValueError` 等。

```text
+-------------------------------------------------------------+
| Built-in Scope (B) e.g., len, str, Exception                |
|  +-------------------------------------------------------+  |
|  | Global Scope (G) e.g., module_var, global_func        |  |
|  |  +-------------------------------------------------+  |  |
|  |  | Enclosing Scope (E) e.g., outer_func's local    |  |  |
|  |  |  +-------------------------------------------+  |  |  |
|  |  |  | Local Scope (L) e.g., inner_func's local  |  |  |  |
|  |  |  +-------------------------------------------+  |  |  |
|  |  +-------------------------------------------------+  |  |
|  +-------------------------------------------------------+  |
+-------------------------------------------------------------+
```

## 2. 什么是闭包？

简而言之，**闭包（Closure）**是一个函数对象，它记住了自己被定义时所处的词法环境，无论该函数后续在哪里被调用，它都能访问这个环境中的变量。

在嵌套函数中，如果内部函数引用了外部函数的局部变量（这些变量对于内部函数来说被称为**自由变量（Free Variables）**），并且外部函数将这个内部函数作为对象返回，那么这个返回的内部函数就构成了一个闭包。

通常，当一个外部函数执行完毕并返回时，它的局部作用域（即在 CPython 中对应的 `PyFrameObject` 栈帧）会被销毁，其局部的临时变量也应该随之被垃圾回收。然而，闭包机制打破了这一生存期限制，使自由变量得以“存活”在内存中，直到闭包函数本身被销毁。

---

## 3. 自由变量与 Cell 对象

CPython 为了实现“延长自由变量生命周期”这一功能，引入了 **Cell 对象（`PyCellObject`）**。

1. **编译期识别**：在将 `.py` 源代码编译成字节码时，CPython 编译器会扫描函数体，识别出哪些变量是“在外层定义但在内层被引用”的自由变量。
2. **Cell 对象创建**：对于这些变量，外层函数不会直接将其值存储在快速局部的局部变量表（`fast locals`）中，而是为其分配一个 Cell 对象，并将实际的值存放在 Cell 内。
3. **闭包携带**：内层函数创建时，会持有一个包含这些 Cell 对象的元组，并绑定到自身的 `__closure__` 属性上。

这种“间接引用”的设计，使得无论是外层函数修改该变量，还是内层闭包修改该变量，它们修改的都是同一个 Cell 对象中的值。

---

## 4. 装饰器作用域与状态绑定

为什么说装饰器本质上就是闭包的实际工程应用？我们来看一段最经典的函数装饰器结构：

```python
def my_decorator(func):
    # func 对于 wrapper 来说是一个自由变量
    def wrapper(*args, **kwargs):
        print("Before function execution")
        # 通过闭包记住的 func 变量进行调用
        result = func(*args, **kwargs)
        print("After function execution")
        return result
    return wrapper
```

在这段代码中：
* `my_decorator` 是外层函数。
* `wrapper` 是内层函数。
* `func` 是外层函数的参数（等同于外层局部变量），被 `wrapper` 引用，因此成为 `wrapper` 的**自由变量**。
* 当 `@my_decorator` 作用于目标函数并被解释器求值时，返回的 `wrapper` 就是一个携带了指向原函数 `func` 的 Cell 对象的闭包。

在接下来的章节中，我们将使用反汇编工具 `dis`，从字节码层面逐条指令拆解这个绑定过程，并深入探索在多层嵌套装饰器中，这些 Cell 引用和执行栈帧是如何进行压栈、寻址与弹栈的。
