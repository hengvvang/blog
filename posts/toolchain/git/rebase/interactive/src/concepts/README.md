# 合并与变基

在深入使用交互式变基之前，我们首先需要从宏观和微观两个层面理解 Git 分支集成的基石概念。分支集成是协同开发的核心，而 Git 提供了两种主要流派：**合并（Merge）** 与 **变基（Rebase）**。

## 1. 合并与变基的哲学差异

这两种机制代表了两种不同的版本控制哲学：
- **历史即事实（History as a Record of Fact）**：主张提交历史应当是项目实际发生过程的真实记录。哪怕本地提交再琐碎、合并关系再复杂，都应当原封不动地保留。这是 `git merge` 的核心理念。
- **历史即叙事（History as a Published Story）**：主张提交历史应当是清晰、易读、富有逻辑的开发演进说明书。无关的调试过程、拼写纠错等噪音应当在推送到共享分支前被修剪和合并，呈现给团队的应当是一条逻辑清晰的线性故事线。这是 `git rebase` 的核心理念。

---

## 2. 提交历史图 (Commit History Graph)

在 Git 中，提交历史并不是线性的磁带，而是一个由提交节点（Commit Node）构成的**有向无环图（DAG）**。
每一个提交节点都包含指向其父节点（Parent）的指针。
- **分叉（Forking）**：当两个分支基于同一个祖先提交，分别在其上进行了新的修改并提交时，DAG 中就产生了两条分叉的路径。
- **集成（Integration）**：将这两条路径的修改合并回主干的过程，就是集成的本质。

---

## 3. 快速向前 (Fast-Forward) 与 三方合并 (Three-Way Merge)

根据集成的拓扑状态，Git 在执行合并时会采取不同的策略：

### A. 快速向前合并 (Fast-Forward)
如果目标分支（如 `main`）自当前分支（如 `feature`）分叉以来没有发生过任何新的提交，那么 Git 在合并时只需要简单地将指针向前移动，指向 `feature` 的最新提交。这种操作没有产生额外的合并提交。

### B. 三方合并 (Three-Way Merge / Non-Fast-Forward)
如果两个分支各自都有新的提交，Git 无法通过移动指针完成合并。它会寻找两者的**最近公共祖先（Common Ancestor）**，并对三方（公共祖先、分支 A 最新提交、分支 B 最新提交）进行差异分析，最终生成一个拥有两个父指针的 **Merge Commit**。

---

## 4. 分支集成模式

在实际工程中，团队需要建立标准化的分支集成规范：
1. **完全 Merge 流**：所有 Feature 分支都通过 `git merge` 合并到 `main`，适合需要绝对追溯历史、不介意合并网络图复杂的团队。
2. **变基后 Merge 流**：本地开发分支首先在 `main` 顶端执行 Rebase，将本地提交整理为干净的线性历史，然后切回 `main` 执行 `git merge --ff-only` 将修改合入，保持主分支的单线拓扑。
3. **Squash Merge 流**：在 GitHub/GitLab 平台合并 Pull Request 时选择 Squash and Merge，将整个分支的所有提交压缩为一个提交，再合入主干。
