# 链接器符号与嵌入式交互

当链接器根据链接脚本确定好各程序段的内存位置后，程序还需要在启动时（Runtime Startup）知道这些内存的边界地址。例如，`.data` 段在哪里开始和结束，`.bss` 段从何处开始清零，以及堆栈的边界在何处。

本部分将深入研究如何在 C/C++ 代码中安全、正确地访问链接脚本中定义的各种符号，以及如何进行静态内存审计。

## 链接器符号物理地址 vs C 变量寻址机制

在 C 语言中，任何全局变量都有一个“物理存储空间”和“存储的值”。而链接脚本定义的符号，**仅代表一个绝对的内存地址**，并不在内存中占据任何实际字节。

下图展示了二者在编译器和链接器处理上的本质区别：

```text
C 语言全局变量 (如: int my_var = 0x12345678;)
+---------------------+---------------------+
| 符号名称 (Symbol)   | 内存地址 (Address)  | ---> 指向存储该值的物理 RAM 空间 (4 字节)
| my_var              | 0x20001004          |      内容为：[ 0x78 | 0x56 | 0x34 | 0x12 ]
+---------------------+---------------------+

链接脚本导出的符号 (如: _sdata = .;)
+---------------------+---------------------+
| 符号名称 (Symbol)   | 内存地址 (Address)  | ---> 无任何物理存储字节！该符号的值在符号表中
| _sdata              | 0x20000000          |      即为 0x20000000。
+---------------------+---------------------+
```

因此，在 C 语言中：
* 访问 `my_var` 时，CPU 会读取 `0x20001004` 地址处的内容。
* 访问 `_sdata` 时，若直接写作 `uint32_t val = _sdata;`，CPU 会去读取 `0x20000000` 地址处的内容（可能导致致命错误）。正确的做法是使用取地址符 `&_sdata` 来获取 `0x20000000` 这个地址值本身。
