# 项目结构化与分发

在现代软件工程中，如何合理组织项目目录、管理内部模块间的依赖传递、以及将最终的编译产物打包发布，是构建系统设计的核心课题。本部分将深入探讨多目录项目的结构化布局、Target-Based 依赖关系管理，以及利用 CPack 进行安装包打包分发的技术。

## 1. 结构化布局与目录设计

随着项目规模的增长，把所有源码堆放在单个目录中会导致代码难以维护。规范的项目应当实行**模块化物理隔离**：
- **`src/`**：主应用程序或顶层逻辑的实现。
- **`include/`**：项目对外公开的全局公共头文件。
- **`lib/`**：项目内部划分的各个独立子模块或第三方库。
- **`tests/`**：单元测试和集成测试代码。

每个包含源码的目录都应该有一个独立的 `CMakeLists.txt`，由顶层 `CMakeLists.txt` 通过 `add_subdirectory()` 关联起来，从而形成清晰的层级依赖树。

## 2. 目标依赖可见性 (PUBLIC / PRIVATE / INTERFACE)

在面向目标的 CMake (Target-Based CMake) 中，我们将一切编译产物抽象为 **Target**（目标）。Target 不仅代表二进制文件，还包含了描述其如何编译、如何被其他模块链接的**属性（Properties）**，例如头文件搜索目录、宏定义、编译选项等。

当 Target B 链接 Target A 时（`target_link_libraries(B <VISIBILITY> A)`），A 的属性将以不同的规则传播给 B：
- **`PRIVATE`**：属性仅供 Target A 自身编译使用，不向 Target B 传播。
- **`INTERFACE`**：属性自身编译时不需要，但任何链接它的使用者（如 Target B）必须使用。
- **`PUBLIC`**：它是 `PRIVATE` 和 `INTERFACE` 的并集，Target A 自己需要，外部链接者 Target B 也同样需要。

```text
Target A 属性传播至 Target B (target_link_libraries(B <VISIBILITY> A))
+------------------+-----------------------------+-----------------------------+
| 可见性修饰符     | 编译 Target A 本身时是否使用| 编译 Target B 本身时是否使用|
+------------------+-----------------------------+-----------------------------+
| PRIVATE          |             是              |             否              |
| INTERFACE        |             否              |             是              |
| PUBLIC           |             是              |             是              |
+------------------+-----------------------------+-----------------------------+
```

## 3. CPack 分发与打包

在构建完成后，如何将生成的可执行文件、共享库、头文件以及配置文件打包成安装包分发给用户？CMake 提供了内建的 **CPack** 模块：
1. **安装指令**：在各自目录的 `CMakeLists.txt` 中使用 `install(TARGETS ... DESTINATION ...)` 指令定义好安装规则，指明哪些文件应该被安装到系统的哪些目录（如 `bin/`、`lib/`、`include/`）。
2. **打包配置**：在顶层 `CMakeLists.txt` 尾部配置 CPack 变量（如包名、版本、维护者等），并使用 `include(CPack)`。
3. **执行打包**：使用 `cpack` 命令行工具，可以一键打包为 `.zip`、`.tar.gz` 压缩包，或者平台专属的二进制安装包（如 Linux 下的 `.deb` / `.rpm`，Windows 下的 NSIS 安装器等）。
