# 01 ESP32 Wi-Fi 架构与 LwIP 协议栈

ESP32 芯片之所以能够在极其受限的内存与功耗约束下，提供高吞吐量的无线网络连接，归功于其软硬件紧密协同的 Wi-Fi 与 TCP/IP 架构。在 ESP-IDF 开发框架中，无线子系统由闭源的底层 Wi-Fi 驱动（乐鑫提供）、轻量级开源 TCP/IP 协议栈（LwIP）以及上层应用接口抽象层（`esp_netif`）共同构建。

理解这些组件在内存空间、执行线程以及硬件中断中的工作机制，是进行高稳定性网络编程的基础。

---

## 1.1 ESP32 Wi-Fi 协议栈层次结构

ESP32 Wi-Fi 栈的设计遵循了类似于 OSI 模型的分层架构。下图展示了数据包从物理天线到应用层 Socket 的流转途径，以及各层在 ESP-IDF 中的边界划分：

```mermaid
graph TD
    subgraph 物理硬件层 (Hardware Layer)
        RF["射频与物理层 (RF / PHY)"]
        MAC["802.11 MAC 硬件加速器"]
    end

    subgraph 闭源驱动层 (Closed-source Driver)
        PHY_DRV["PHY 驱动 / 校准控制"]
        WIFI_DRV["Wi-Fi Core 驱动 (libwifi.a)"]
        TX_RX_QUEUE["DMA 发送/接收环形缓冲区"]
    end

    subgraph 网络抽象与协议层 (Network & Protocol)
        ESP_NETIF["esp_netif 适配器"]
        LWIP["LwIP 协议栈内核 (IP / TCP / UDP)"]
    end

    subgraph 应用层 (Application Layer)
        APP_SOCKET["BSD Socket API / HTTP / MQTT"]
        EVENT_LOOP["系统事件循环 (Event Loop)"]
    end

    %% 数据流向
    RF <--> MAC
    MAC <--> TX_RX_QUEUE
    TX_RX_QUEUE <--> WIFI_DRV
    WIFI_DRV <--> ESP_NETIF
    ESP_NETIF <--> LWIP
    LWIP <--> APP_SOCKET
    
    %% 事件通知
    WIFI_DRV -. 触发事件 .-> EVENT_LOOP
    LWIP -. 触发事件 .-> EVENT_LOOP
```

### 1.1.1 硬件与物理层 (RF / PHY & MAC)
ESP32 集成了 2.4 GHz 接收机和发射机、天线开关、射频巴伦（Balun）、低噪声放大器（LNA）、功率放大器（PA）以及双工滤波器。其 802.11 MAC 层提供硬件级的加密/解密加速（WEP, WPA/WPA2/WPA3 CCMP, TKIP, BIP）、硬件帧过滤、信道载波监听（CSMA/CA）以及帧确认（ACK）的自动发送。

### 1.1.2 闭源 Wi-Fi 驱动层
由于无线合规性、专有校准算法和协议细节的敏感性，乐鑫将 Wi-Fi 核心驱动以静态库（如 `libwifi.a`、`libphy.a`、`librtc.a` 等）的形式分发。该层负责：
- **速率控制（Rate Control）**：根据信噪比（SNR）和包丢失率，动态切换 802.11 的调制与编码策略（MCS）。
- **扫描与建连管理**：扫描信道、解析 Beacon 帧、发起 Probe Request 并完成四步握手（4-Way Handshake）。
- **省电管理（Power Management）**：与 FreeRTOS 调度器配合，在 Modem-sleep 模式下精确控制射频芯片的唤醒时机（根据 DTIM 间隔）。

### 1.1.3 网络接口层 (`esp_netif`)
在 ESP-IDF v4.x 及之前的版本中，LwIP 与 Wi-Fi 驱动直接耦合，移植性极差。自 v5.x 起，引入了 **`esp_netif`（ESP Network Interface）**，作为一种与介质无关的网络接口适配层。
`esp_netif` 屏蔽了底层硬件（如 Wi-Fi、以太网、4G/5G 调制解调器）的差异，向 LwIP 提供统一的网络接口（`netif`），并向上层应用暴露统一的配置和控制 API。

## 1.2 任务（线程）模型与优先级设计

ESP32 采用双核 Xtensa LX6/LX7 处理器（通常称为 Protocol CPU - PRO_CPU 和 Application CPU - APP_CPU）。为了保证实时性，无线协议栈采用了多任务并发模型，各任务在 FreeRTOS 中的优先级分布具有极其严格的要求。

### 1.2.1 核心任务及其职责

在 Wi-Fi 启动后，系统中会有三个关键任务协同工作：

| 任务名称 | 默认优先级 | 运行内核 (Core Binding) | 职责 |
| :--- | :--- | :--- | :--- |
| **`wifi` 任务** | 23 | 通常绑定到 PRO_CPU (Core 0) | 处理 Wi-Fi 驱动底层的事件，从硬件 FIFO 中读取 802.11 帧，或者将发送帧推入 MAC 环形缓冲区。它需要极高的实时性，防止 FIFO 溢出。 |
| **`tiT` (tcpip) 任务** | 18 | 通常绑定到 PRO_CPU (Core 0) | LwIP 协议栈的核心运行线程。所有经过 IP 层、TCP 层、UDP 层的数据包及定时器（重传、ARP 超时等）都在此任务中处理。 |
| **`app_main` / 应用任务** | 5 (可配置) | 通常运行在 APP_CPU (Core 1) | 用户编写的业务逻辑（如建立 HTTP 连接、读写 Socket、数据解析）。 |

> [!WARNING]
> **优先级陷阱**：应用层任务的优先级**绝对不能**高于或等于 `wifi` 任务 (23) 或 `tcpip` 任务 (18)。如果应用任务占用了 100% 的 CPU（例如在一个死循环中运行且未交出 CPU 控制权），并且优先级高于 18，将直接导致 LwIP 无法处理定时器与 ACK 包，触发 Wi-Fi 频繁断开连接（如 `WIFI_REASON_ASSOC_TOOMANY` 或握手超时）。

### 1.2.2 数据包在多任务间的流转时序

        | 1. 硬件 RX 中断触发  |                     |                     |

## 1.3 协议栈内存管理与缓存优化

在嵌入式系统中，内存是极其昂贵的资源。当 ESP32 进行高速网络传输时（例如通过 TCP 进行 OTA 固件下载或传输视频流），内存缓冲区的配置直接决定了吞吐量极限和系统稳定性。

### 1.3.1 Wi-Fi 驱动缓冲区 (TX/RX Buffers)
ESP32 Wi-Fi 驱动在内部维护了一组静态或动态的环形缓冲区。
- **静态分配**：在 Wi-Fi 初始化时预先分配固定数量的内存块，保证任何情况下都不会因为内存碎片而无法发送/接收数据。
- **动态分配**：根据当前流量动态向系统堆（Heap）申请内存，空闲时释放。在可用 SRAM 紧缺时使用，但如果发生严重的堆碎片，可能会因为分配缓冲区失败而丢包。

在 `wifi_init_config_t` 中，有两个关键参数控制缓冲区数量：
- `static_rx_buf_num`：静态接收缓冲区数量（默认 10）。每个缓冲区大小约为 1.6 KB。
- `dynamic_rx_buf_num`：动态接收缓冲区数量（默认 32）。

### 1.3.2 LwIP 内存管理 (pbuf 机制)
LwIP 通过 `pbuf`（Packet Buffer）结构管理数据包内存。`pbuf` 主要有以下三种类型：
1. **`PBUF_RAM`**：在内存堆中动态分配的连续空间。常用于协议栈主动生成的发送数据包。
2. **`PBUF_POOL`**：从预先分配的固定大小的内存池中申请的块。Wi-Fi 驱动在收到硬件帧后，会将其封装进通过 `PBUF_POOL` 申请的 `pbuf` 中，再传递给 LwIP。
3. **`PBUF_ROM` / `PBUF_REF`**：不占用数据拷贝内存，仅包含指向物理 ROM 或 RAM 中已有数据的指针。常用于发送静态网页等不需要修改的数据。

```
PBUF_RAM 结构示意图 (连续内存，包含首部和有效载荷):
+-----------------------------------+-----------------------------------+
|  pbuf 结构体 (next, payload, len)  |        实际网络数据帧 (Payload)    |
+-----------------------------------+-----------------------------------+

PBUF_POOL 链表示意图 (非连续物理内存，通过 next 指针链接):
+-----------+    +-----------+    +-----------+
| pbuf 头 1 | -> | pbuf 头 2 | -> | pbuf 头 3 |
+-----------+    +-----------+    +-----------+
| payload 1 |    | payload 2 |    | payload 3 |
+-----------+    +-----------+    +-----------+
```

### 1.3.3 AMPDU (聚合 MAC 协议数据单元) 调优
为了提高吞吐量，802.11n 引入了帧聚合技术（AMPDU 和 AMSDU），即把多个子帧打包成一个物理帧发送，以减少物理层报头和竞争信道所带来的开销。
- **AMPDU 接收窗口大小**：在 `wifi_config_t` 中通过 `rx_ba_window` 配置。如果接收窗口设置得太小（例如小于 6），在高速传输时会导致频繁丢包重传；如果设置得太大（例如 32），则会占用大量的底层 SRAM 缓冲区（每个窗口位置都对应一个待重组的包）。对于普通 IoT 设备，建议将其设置为 `6` 到 `16` 之间的平衡值。
