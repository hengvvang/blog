# 第一章：BLE 层次架构与核心概念辨析

低功耗蓝牙 (BLE) 并不是经典蓝牙 (Classic Bluetooth) 的简化版本，而是一套从底层的物理层 (PHY) 到上层的配置文件 (Profile) 进行了完全重新定义的低功耗无线通信标准。

为了在 ESP32 上开发出具备高吞吐量、低功耗、运行稳定的生产级 GATT 服务器，我们必须首先从协议栈的物理时序、内存映射及逻辑交互等维度，对 BLE 的核心概念进行系统化剖析。

---

## 1. BLE 协议栈分层与数据封装

BLE 协议栈在逻辑上呈现高度模块化的结构，主要由**控制器层 (Controller)**、**主机层 (Host)** 和**应用层 (Application)** 三部分组成。它们之间的交互定义了数据的封装与流转路径。

### 1.1 协议栈各层数据封装流向

当应用层需要发送一段业务数据时，该数据会自顶向下穿过协议栈的各个层次，每一层都会在其头部或尾部添加控制信息。以下是完整的协议栈数据封装与映射关系：

```
       +-------------------------------------------------------+
 应用层 |                 User Data (Payload)                   |
       +-------------------------------------------------------+
                               |
                               v (映射为特定特征的 Value)
       +-------------------+-----------------------------------+
 ATT层  | ATT Opcode (1B)   | Attribute Value (Data Payload)    |
       +-------------------+-----------------------------------+
       |<------------- ATT PDU (最大为 MTU 大小) -------------->|
                               |
                               v (进行通道复用与分片)
       +-------------------+-----------------------------------+
L2CAP层 | Length (2B)       | Channel ID (2B) | ATT Payload     |
       +-------------------+------------------+----------------+
       |<----------------------- L2CAP PDU ------------------->|
                               |
                               v (添加链路层包头与校验)
       +---------+--------------------+------------------------+---------+
LL层    | Preamble| Access Address(4B) | PDU Header(2B) |Payload | CRC(3B) |
       +---------+--------------------+------------------------+---------+
       |<------------------------ Link Layer Packet -------------------->|
                               |
                               v (射频调制：GFSK 调制)
 PHY层  |                 2.4 GHz ISM 物理载波波形                |
       +-----------------------------------------------------------------+
```

* **PHY（物理层）：** 运行在全球通用的 2.4 GHz ISM 频段，划分了 40 个 RF 信道（37、38、39 信道为主要广播信道，0 ~ 36 信道为数据通信信道）。采用高斯频移键控 (GFSK) 调制，数据速率支持 1 Mbps（经典 BLE）以及在蓝牙 5.0 规范中引入的 2 Mbps（高吞吐量物理层）和 Coded PHY（高灵敏度远距离物理层）。
* **LL（链路层）：** 协议栈中最底层的状态控制器，控制设备的射频发射时序，定义了各种状态的转移，并提供防冲突、自适应跳频 (AFH)、数据包确认重传与底层 AES-128 加密机制。
* **HCI/VHCI（主机控制器接口）：** 控制器和主机的通信通路。在 ESP32 这种单芯片 SoC 中，主控内核与蓝牙控制器共用同一物理 RAM，因此不通过 UART 等慢速总线，而是采用基于 FreeRTOS 环形缓冲区及软件中断的 **VHCI (Virtual HCI)** 进行高效的无拷贝进程间通信。
* **L2CAP（逻辑链路控制与适配协议）：** 封装上层的 ATT 和 SMP 协议，将其多路复用到链路层的逻辑信道上。它负责对超出底层 LL 最大包长限制的数据进行拆包 (Segmentation) 与重组 (Reassembly)。
* **ATT（属性协议）：** 一个扁平的客户端/服务器协议。它把设备上的所有数据都抽象成“属性”，定义了属性的基本格式和对其进行 Read、Write、Notify、Indicate 的基本操作。
* **GATT（通用属性配置文件）：** 建立在 ATT 协议之上，将扁平的属性归纳、整理并抽象为有层级结构的“服务”和“特征”，便于应用层调用。
* **GAP（通用访问配置文件）：** 负责控制广播模式、建立连接、管理配对安全、绑定以及链路参数协商。

## 2. 链路层 (Link Layer) 状态机

链路层 (LL) 内部运行着一个极其严格的实时状态机。设备在任何时刻都必然处于以下五种状态之一：

```
                    +-------------------+
                    |      Standby      | <---------- 开启电源
                    +-------------------+
                       /      |      \
        主动启动广播     /       |       \     开启扫描
                    v         |         v
       +-----------------+    |    +-----------------+
       |   Advertising   |    |    |    Scanning     |
       +-----------------+    |    +-----------------+
               |              |             |
   收到来自     |              |             | 扫到目标设备并
   主机的连接   |              |             | 主动发起连接
   请求信号     |              v             |
               |      +-----------------+   |
               |      |   Initiating    | <--+
               |      +-----------------+
               v              |
       +-----------------+    | 建立连接成功
       |   Connection    | <--+
       |  (Master/Slave) |
       +-----------------+
```

* **Standby（待机状态）：** 处于休眠或省电模式，射频关闭，是所有状态的起点。
* **Advertising（广播状态）：** 周期性在 37、38、39 信道上广播自己的存在，并监听客户端发来的扫描请求或连接包。
* **Scanning（扫描状态）：** 接收监听空口中的广播数据，可细分为**被动扫描**（仅接收广播数据）与**主动扫描**（接收广播数据后，主动向广播者发送扫描请求 `SCAN_REQ` 以获取其扫描响应数据 `SCAN_RSP`）。
* **Initiating（发起状态）：** 监听特定外设的广播，并在收到其广播的瞬间发送连接建立指示包 (`CONNECT_IND`)。
* **Connection（连接状态）：** 设备成功加入点对点网络。连接中包含两种角色：
  - **Master (主机)：** 发起连接的设备（处于 Initiating 状态转入）。它决定了连接的跳频时序、时钟基准与同步窗口。
  - **Slave (从机)：** 广播并接受连接的设备（处于 Advertising 状态转入）。它必须跟随主机的跳频窗口与时序进行射频收发。

## 3. GAP 连接参数与时序规避

为了保证连接稳定且实现极低功耗，GAP 在建立物理链路时引入了多项关键时序参数。

### 3.1 广播周期与伪随机延迟

外设在广播时，如果使用完全固定的时间间隔，一旦有多个设备同时启动，极易因为相位对齐而产生持续性射频碰撞。为了规避这一冲突，BLE 协议在设定的基本广播间隔（$T_{\text{adv\_interval}}$）上加入了一个 `0 ~ 10 ms` 的伪随机时间抖动值（$T_{\text{adv\_delay}}$）：

$$\text{Actual Advertising Interval} = T_{\text{adv\_interval}} + T_{\text{adv\_delay}}$$

链路层会在每一个广播事件（Advertising Event）中，依次在 37、38、39 信道发射数据，并短暂打开 Rx 窗口接收响应：

```
 信道 37: [ ADV_IND ] ---> [ Rx Window ]
 信道 38:             [ ADV_IND ] ---> [ Rx Window ]
 信道 39:                         [ ADV_IND ] ---> [ Rx Window ]
 |<--------------------- 广播事件 (Advertising Event) --------------------->|
```

### 3.2 核心连接参数

当连接建立后，双方设备将约定按照**连接事件 (Connection Event)** 的频率在 0 ~ 36 信道上进行射频同步。决定这一通信品质的参数有三个：

1. **Connection Interval (连接间隔)：** 两次连接事件之间的物理时间距离。以 1.25 ms 为基本步长单位，范围为 7.5 ms 至 4.0 s。连接间隔越小，数据包交换频率越高，吞吐量越大，但功耗也会呈线性增加。
2. **Slave Latency (从机延迟 / 潜伏期)：** 允许从机在没有数据需要上报时，可以忽略跳过多少个连接事件而不用唤醒射频进行空包应答。例如：当 Slave Latency = 4 时，如果从机无数据上报，它可以连续休眠 4 个连接间隔，直到第 5 个连接事件到达才强制唤醒射频与主机握手。这能显著降低空闲连接下的功耗。
3. **Supervision Timeout (超时监督时间)：** 链路最大失联时间上限。以 10 ms 为单位，范围为 100 ms 至 32.0 s。如果双方在此时间内未发生过一次成功的射频交互（哪怕是空包交互），则判定为断开连接。

> [!WARNING]
> **参数有效性数学约束：**
> 为了保证连接不会因为从机延迟而误判定为超时断开，协议规定所有连接参数必须严格满足以下数学不等式：
> $$\text{Supervision Timeout} > (1 + \text{Slave Latency}) \times \text{Connection Interval} \times 2$$
> 如果开发者在代码中申请了不合法的参数，蓝牙控制器将会直接拒绝此次参数修改请求。

## 4. GATT 属性表 (Attribute Database) 物理布局

GATT 规范的核心是将所有的数据交互实体扁平化地映射到 ATT 属性数据库中。不管是服务定义、特征声明、特征值还是相关的配置描述符，在物理内存中都被统一抽象为 **Attribute 条目**。

### 4.1 数据库结构布局

下图展示了一个标准 GATT 服务器的属性数据库物理内存分布及字段构成：

```
+------------+------------+-----------------------------------------+---------------------+
| 句柄Handle  |  属性UUID  |               属性值 Value              |    访问权限 Perms   |
|  (16-bit)  |  (Type)    |           (Attribute Value)             |  (Access Control)   |
+------------+------------+-----------------------------------------+---------------------+
|   0x0001   |   0x2800   | 0xFFF0 (服务宣告: 值为服务UUID)           | READ-ONLY           |  <-- 服务声明
+------------+------------+-----------------------------------------+---------------------+
|   0x0002   |   0x2803   | [Prop: WRITE, Handle: 0x0003, UUID:F1]  | READ-ONLY           |  <-- 特征A声明
+------------+------------+-----------------------------------------+---------------------+
|   0x0003   |   0xFFF1   | [ 实际特征值：用于存放外部写入的控制数据 ] | WRITE-ONLY (密文)   |  <-- 特征A的值
+------------+------------+-----------------------------------------+---------------------+
|   0x0004   |   0x2803   | [Prop: NOTIFY, Handle:0x0005, UUID:F2]  | READ-ONLY           |  <-- 特征B声明
+------------+------------+-----------------------------------------+---------------------+
|   0x0005   |   0xFFF2   | [ 实际特征值：存放传感器遥测的裸数据 ]     | READ-ONLY           |  <-- 特征B的值
+------------+------------+-----------------------------------------+---------------------+
|   0x0006   |   0x2902   | 0x0001 (CCCD 的值: 指示开启 Notification) | READ-WRITE (明文)   |  <-- 特征B的CCCD
+------------+------------+-----------------------------------------+---------------------+
```

* **Handle (句柄)：** 属性在数据库中的唯一 16 位地址标识（范围 `0x0001 ~ 0xFFFF`），在建表时由协议栈自增分配。客户端通过句柄来进行精确寻址访问。
* **UUID (属性类型)：** 
  - 16-bit UUID：SIG 官方定义的标准 UUID（如 `0x2800` 代表 Primary Service，`0x2803` 代表 Characteristic Declaration，`0x2902` 代表 CCCD）。
  - 128-bit UUID：自定义服务与特征的私有 UUID（如 `0x0000FFF0-0000-1000-8000-00805F9B34FB`）。
* **Value (值)：** 属性所携带的二进制数据流。对于服务声明，其值是服务的 UUID；对于特征声明，其值包含了特征的属性标志位（Read/Write/Notify）以及特征值条目的句柄和 UUID；对于特征值，则是具体的数据。
* **Permissions (权限)：** 控制该条属性的访问机制。可以配置为：
  - `Read / Write`：明文可读、可写。
  - `Read / Write Encrypted`：必须在加密连接下才能访问（需要配对）。
  - `Read / Write Authorized`：访问时需要应用层软件弹出授权确认。

### 4.2 客户端特征配置描述符 (CCCD, 0x2902)

CCCD 是一个极其重要的描述符。它紧跟在支持异步主动推送（Notify 或 Indicate）的特征值条目后面。
* CCCD 的物理属性值是一个 **2 字节的位图 (Bitmap)**。
* 客户端（如手机）通过向该 CCCD 写入不同的值来使能或关闭服务器端的数据推送：
  - 写入 `0x0001`：开启 **Notification**（通知，无确认应答）。
  - 写入 `0x0002`：开启 **Indication**（指示，需要确认应答）。
  - 写入 `0x0000`：关闭所有主动推送。

## 5. GATT 数据交互模式吞吐量与机制辨析

在 GATT 双向数据流中，不同的操作有着不同的流量控制机制，直接决定了通信的时延与最大吞吐量。

| 交互类型 | 发起方 | 确认方式 | 典型空口图示 | 吞吐量特征 | 适用场景 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Read** | Client | Server 回复 Response | `Client --Read Req--> Server` <br> `Client <--Read Rsp--- Server` | 较低，依赖连接间隔的时序握手 | 主机拉取静态配置、设备信息 |
| **Write Request** | Client | Server 回复 Response | `Client --Write Req--> Server` <br> `Client <--Write Rsp--- Server` | 较低，每个连接事件通常只能完成一对交互 | 主机修改阈值、开启关键物理开关 |
| **Write Command (Write No Resp)** | Client | 无应用层应答 | `Client --Write Cmd--> Server` | 极高，允许在一个连接事件内填满多个物理包 | OTA 固件大文件分包传输 |
| **Notification** | Server | 无应用层应答 | `Client <--Notification-- Server` | 极高，不受应用层握手限制，时延最低 | 传感器高速数据采集、心率上报 |
| **Indication** | Server | Client 回复 Confirm | `Client <--Indicate------ Server` <br> `Client --Confirm----> Server` | 较低，下一次指示前必须等待客户端 Confirm | 警报上报、关键状态变化通知 |

通过对上述核心协议层概念的厘清，我们可以发现，在 ESP32 上设计高性能 BLE 应用时，我们需要重点关注：
1. **如何一次性把这一系列复杂的物理属性表高效地部署进内存？**
2. **如何在一个高度异步的事件回调模型中，设计一个保证不阻塞协议栈的 FreeRTOS 并发架构？**

这些问题我们将在接下来的章节中逐一给出生产级的实现方案。
