# 第一部分：Git Flow 分支模型与角色定义

在软件开发生命周期中，多分支协作是团队保障软件交付质量与开发效率的关键手段。Git Flow 模型通过对分支角色的严密定义，建立起一套稳健、规范的多分支协作机制。

本部分将深入分析 Git Flow 中的双核心长期分支与三大短期辅助分支，并明确其命名规范与拓扑演进规则。

---

## 核心分支分类

在 Git Flow 模型中，所有的分支可以划分为以下两大类别：

### 1. 核心长期分支 (Long-lived Branches)
核心分支存在于整个项目的生命周期中，它们不能被删除，代表了项目的核心发布轨迹与集成状态。
- **`main` / `master`**：生产环境发布分支。它代表了绝对稳定、经过完备测试、可随时进行生产部署的代码。每一个在此分支上的 Commit 都代表一个稳定的对外版本。
- **`develop`**：开发集成分支。它是日常新特性集成的汇聚地，代表了下一代版本的最新开发进度。

### 2. 辅助支持分支 (Supporting Branches)
辅助分支是在软件研发的不同阶段（特性开发、发布冷冻、紧急修复）临时拉取的分支，其生命周期是有限的，当其职责完成后会被安全合并并彻底删除。
- **`feature/*`**：特性/功能分支。用于隔离日常新特性的开发。
- **`release/*`**：预发布/发布分支。用于在新版本上线前进行版本冷冻、回归测试与缺陷修复。
- **`hotfix/*`**：紧急修复/补丁分支。用于解决线上运行环境（`main` 分支代码）出现的严重缺陷，具有独立的紧急发布流。

## 命名约定与映射图示

规范的命名可以极大地降低团队内部的沟通成本，并便于 CI/CD 自动化流水线对不同分支执行针对性的校验策略。

```text
[ 长期主干 ]
  main        --> (线上稳定版本，Tag: v1.0.0, v1.1.0)
  develop     --> (日常开发集成点，始终向前演进)

[ 短期辅助 ]
  feature/    --> feature/<issue-id>-<description> (例: feature/PROJ-101-user-login)
  release/    --> release/v<Major>.<Minor>.<Patch> (例: release/v1.1.0)
  hotfix/     --> hotfix/v<Major>.<Minor>.<Patch> (例: hotfix/v1.1.1)
```

在接下来的章节中，我们将详细讨论每个分支的具体职责边界、安全保护准入原则（如禁止 Force Push、强制 Code Review 与 CI 门禁），以及如何在实际项目中安全应用这些规范。
