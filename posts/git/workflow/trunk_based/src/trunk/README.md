# 主干模型与 CI/CD

在现代高效的软件交付体系中，**主干开发（Trunk-Based Development, TBD）** 代表了持续集成（Continuous Integration）的纯粹状态与终极形态。本部分聚焦于主干开发的核心物理模型、分支生命周期约束，以及如何在大规模研发团队中设计高性能、高可靠的 CI/CD 自动门禁与流水线控制系统。

---

## 核心主题与知识框架

本部分由两个核心章节组成，涵盖从底层 Git 冲突算法到企业级流水线设计：

### 1. [第一章：主干开发核心原则与短寿命分支管理机制](tbd-principles.md)
* **主干核心约束**：探讨所有开发者共享单一主干分支（`main`/`master`）、小粒度高频集成的核心工作模式。
* **分叉代价量化**：通过数学模型量化分支隔离时间与冲突率的非线性增长关系，深度剖析 Git 底层三路合并（3-Way Merge）的执行机理与 LCA（最近公共祖先）漂移带来的合并退化风险。
* **短寿命分支最佳实践**：掌握使用短寿命功能分支（Short-lived Feature Branch，生存周期 $< 24$ 小时）的物理边界，以及强制线性提交历史（Rebase vs Merge）的团队规范配置。

### 2. [第二章：大规模团队并行构建与 CI/CD 流水线自动控制](scaling-and-ci-cd.md)
* **流水线自动化门禁（PR Gating）**：详细剖析静态语法检查、依赖漏洞扫描、多阶段自动化测试卡点的企业级构建链路。
* **大规模 Monorepo 增量校验**：分析在单体大仓（Monorepo）场景下如何利用依赖图（Dependency Graph）与增量缓存，避免全量构建带来的 CI 耗时飙升。
* **合并队列（Merge Queue）**：深入分析乐观锁与并发试错链条，彻底解决高频并发提交时的主干崩塌问题。
* **渐进式 CD 与金丝雀发布**：基于监控回显自动化验证发布，并对比特性开关、镜像回退、Git Revert 在不同故障下的自愈实效。

## 持续集成的本质：以小步快跑规避集成地狱

传统的 Git 分支模型（如 Git Flow）鼓励长期隔离开发，将“集成”推迟到发布前夕，这本质上是把技术债向后累积，从而导致了痛苦的“集成地狱”（Merge Hell）。

主干开发则反其道而行之：
1. **小粒度（Small Batches）**：将庞大的需求拆解为可以在数小时或一天内完成并测试通过的代码片。
2. **高频集成（High-Frequency Integration）**：每日多次拉取主干并推送合并，使得冲突在最微小的状态下被当场暴露和解决。
3. **主干常绿（Keep the Trunk Green）**：通过极其严格的自动化流水线，确保任何时刻主干分支代码都具备生产环境可部署的质量。

本篇将带你建立严密的持续集成思维，从根本上优化团队的研发交付效率。
