# Git Reflog 简介

在日常的版本控制实践中，开发者们不可避免地会遇到这类令人战栗的场景：
- 执行了 `git reset --hard HEAD~5`，回滚了本地提交，却突然发现其中包含尚未推送到远程的重要修改；
- 误删除了一个开发了数周但尚未合并的本地分支（`git branch -D feature-x`）；
- 在进行复杂的 `git rebase` 或 `git cherry-pick` 时发生冲突，为了“推倒重来”执行了错误的清理命令，导致工作区和提交历史一片混乱。

对于初学者甚至是中高级工程师而言，这些场景往往意味着“毁灭性的代码丢失”。然而，在这些看似“无可挽回”的灾难背后，Git 实际上悄悄为我们保留了一道终极防线——**引用日志（Reference Logs，简称 Reflog）**。

本书将从底层数据结构、对象模型以及 Git 管道命令（Plumbing Commands）的视角，带您深入探索 Git Reflog 的内部工作机制，帮助您在面对代码丢失时能够沉着应对，利用底层的恢复机制找回任何曾经提交过（甚至仅暂存过）的代码。

---

## 什么是 Git Reflog？

简单来说，**Reflog 是 Git 用来记录本地仓库中引用（References，如分支指针、HEAD 指针、标签等）更新历史的本地审计机制**。

每当你在本地仓库中执行任何会改变引用指向的操作（例如 `commit`、`checkout`、`reset`、`rebase`、`merge`、`pull` 等），Git 都会在对应的引用日志文件中追加一条记录，标明该引用在什么时间、由谁、因为什么操作，从哪一个 Commit SHA-1 转移到了另一个 Commit SHA-1。这种机制相当于给你的指针操作安装了一个“黑匣子”，忠实记录着每一次物理移动。

### 核心物理模型

下图展示了 HEAD 指针、分支指针、提交对象（Commit Object）与它们所对应的 Reflog 审计日志之间的物理关系：

```text
                     ┌────────────────┐
                     │   .git/HEAD    │ (符号引用，指向当前所在的分支)
                     └───────┬────────┘
                             │
                             ▼
              ┌──────────────────────────────┐
              │  .git/refs/heads/master      │ (普通引用，指向具体的提交哈希)
              └──────────────┬───────────────┘
                             │
       ┌─────────────────────┴──────────────────────┐
       ▼                                            ▼
┌──────────────┐                             ┌──────────────┐
│ Commit C2    │                             │ Commit C1    │
│ (SHA: d6855) │ ───(parent 指向旧提交)───>  │ (SHA: 96b86) │
└──────────────┘                             └──────────────┘
       ▲                                            ▲
       │                                            │
       │  (每次指针位置改变时，都会向对应的物理日志追加记录)
       │                                            │
┌──────┴────────────────────────────────────────────┴───────┐
│              .git/logs/refs/heads/master                  │ (分支更新日志)
├───────────────────────────────────────────────────────────┤
│ 96b86f8... d685501... hengvvang <...> 1779951600: commit  │
└───────────────────────────────────────────────────────────┘
                            │
                            ▼
┌───────────────────────────────────────────────────────────┐
│                    .git/logs/HEAD                         │ (HEAD 更新日志)
├───────────────────────────────────────────────────────────┤
│ 96b86f8... d685501... hengvvang <...> 1779951600: commit  │
└───────────────────────────────────────────────────────────┘
```

## Reflog 与 Git Log 的本质区别

很多初学者容易混淆 `git reflog` 与 `git log`。下表对比了两者的核心差异：

| 维度 | Git Log (常规日志) | Git Reflog (引用日志) |
| :--- | :--- | :--- |
| **物理数据源** | 提交历史的有向无环图（Commit DAG） | 本地引用更新的顺序文本日志（Chronological Log） |
| **共享与传输** | 共享的、跨仓库的（会随 `push` / `fetch` 传输） | 纯本地的（从不参与网络传输，每个本地克隆独有） |
| **生命周期** | 永久保留（只要能从任何分支/标签追溯到该提交） | 具有有效期限制（默认 30~90 天，过期后会被垃圾回收） |
| **审计性质** | 逻辑上的版本演进历史（呈现最终的树图） | 物理上的指针移动审计痕迹（呈现开发者的操作步骤） |
| **包含范围** | 仅包含当前分支/历史可达的有效提交 | 包含所有“已废弃”的、悬空的提交（Dangling Commits） |
| **工作区变更** | 无法直接捕获未提交的暂存内容 | 可以间接作为寻找因重置丢失的暂存区 Blob 对象的抓手 |

## 本书内容结构

本书分为两个核心部分，共三个章节，由浅入深地为您剖析：

### 第一部分：引用指针与 Reflog 变更日志
* **[引用与变更日志](logs/README.md)**：介绍引用在 Git 内部的存储目录结构（HEAD、heads、tags、remotes）以及引用变更记录的触发机制。
* **[第一章：Git 引用指针机制与 Reflog 运行日志](logs/references-and-reflog.md)**：深入剖析 `.git` 目录的物理结构，探寻 `.git/refs/` 与 `.git/logs/` 的对应关系。通过直接读取和解析底层的日志文件，掌握 Reflog 条目的具体字节格式、写入触发时机，以及 HEAD 指针与分支指针 Reflog 的独立性，并提供使用 Shell/Awk 脚本直接读取原始 Reflog 的实战。

### 第二部分：灾难恢复、垃圾回收与生命周期
* **[灾难恢复与 GC](recovery/README.md)**：本节引言介绍误操作恢复的概念、不可达与悬空对象的定义、以及垃圾回收（GC）和修剪（Prune）的基本流程。
* **[第二章：基于 Reflog 的误删分支与丢失 Commit 灾难恢复](recovery/recovering-lost-commits.md)**：本章进入实战场景。我们将模拟多种常见的“代码丢失”灾难，并使用 `git reflog`、`git log -g`、`git fsck --lost-found` 等工具逐步分析并成功定位、恢复那些已经成为“孤儿（Orphan）”或“悬空（Dangling）”的 Commit、分支甚至未提交（但已 `git add`）的暂存区代码。
* **[第三章：Git 垃圾回收 (GC) 与引用生命周期清理](recovery/maintenance-and-expiry.md)**：本章详细讲解 Git 垃圾回收（Garbage Collection）的触发机制，剖析 `gc.reflogExpire` 与 `gc.reflogExpireUnreachable` 等关键配置项对引用日志生命周期的控制逻辑，并指导您如何编写脚本来安全地进行 Reflog 审计与手动清理，甚至执行针对敏感数据（如密码泄漏）的彻底物理擦除。

## 学习目标

通过阅读本书，您将达到以下技术深度：
1. **源码与物理级理解**：能够脱离 Git CLI 抽象，直接用命令行和脚本解析 `.git/logs/` 下的原始日志，理解其底层文本存储协议与多进程更新下的排他锁（`.lock`）机制。
2. **灾难恢复专家**：掌握科学的排查链路，无论是 `reset --hard`、分支强删还是 `rebase` 失败，都能迅速画出局部的 Commit 图谱，精确定位 SHA-1 并选择最合适的策略恢复。
3. **运维与调优能力**：理解 Git 的自动修剪（Pruning）策略，能够合理配置大型项目中的 GC 参数，保证本地开发与中央服务器的性能平衡。
