# 灾难恢复与 GC

在理解了 Git 引用的底层布局和 Reflog 的数据格式后，我们将目光转向这些机制的实际应用：**如何在遭遇破坏性操作时进行数据抢救，以及 Git 是如何管理这些悬空数据生命周期的**。

本部分将聚焦于 Git 的容灾机制与垃圾回收策略。

---

## 灾难恢复机制

当我们在本地仓库执行了破坏性操作（如强行回滚、强删未合并分支），本以为数据已经永久丢失，但在 Git 底层，这些提交对象（Commit）、目录树对象（Tree）和文件内容对象（Blob）依然完整保留在 `.git/objects/` 数据库中。

我们可以通过两种核心途径定位并恢复这些数据：
1. **通过 Reflog 检索**：利用本地引用日志（HEAD 或分支日志），查找发生误操作前引用所指向的 Commit 哈希值。这是最快、最直观的恢复方式。
2. **通过 `git fsck` 扫描**：如果引用的日志文件已被清除或已过期，我们可以直接调用文件系统一致性检查工具（FSCK），遍历整个对象数据库，过滤出所有不被任何引用指向的“悬空（Dangling）”对象，从而手工还原。

---

## 垃圾回收 (GC) 与修剪 (Prune)

Git 的对象数据库不可能无限制地增长。为了保持系统的高效运转，Git 引入了**垃圾回收 (Garbage Collection, GC)** 机制：

* **垃圾判定**：当一个对象在有向无环图（DAG）中不可达，且其在所有的 Reflog 中也已经过期（没有被任何日志记录指向）时，该对象便被判定为“垃圾”。
* **过期机制 (Expiry)**：Git 对这些垃圾对象设有“缓冲期”（默认 14 天到 90 天不等）。在这期间，对象依然驻留在磁盘上，处于可抢救状态。
* **物理修剪 (Pruning)**：当垃圾对象超过了设定的过期阈值，执行 `git gc` 或 `git prune` 时，Git 将会物理删除这些松散对象，彻底释放磁盘空间。

---

## Git 对象生命周期图谱

下图展示了从工作区文件被暂存，到提交、回滚，再到最终被物理修剪的完整生命周期：

```text
  [ 工作区文件 ]
        │
        │ (git add) ─── 立即创建物理松散 Blob 对象
        ▼
  [ 暂存区索引 (Index) ] 
        │
        │ (git commit) ─┐
        ▼               │ 正常分支推进
  [ 可达提交对象 (Reachable Commit) ] ───> [ 成为历史的一部分 (随 push 共享) ]
        │
        │ (git reset --hard / git branch -D)
        ▼
  [ 不可达/悬空提交 (Unreachable / Dangling Commit) ]
        │
        │ ◄───────────────────┐ (在过期时间内，可通过 Reflog 或 git fsck 恢复)
        │                     │
        │ 保留期 (30 ~ 90 天) │
        │                     │
        ▼                     │ 
   [ 引用日志过期 ] ──────────┘ 
        │ (Commit 失去 Reflog 的指向)
        ▼
   [ 彻底孤立的垃圾对象 ] 
        │
        │ (超过 gc.pruneExpire，执行 git gc / git prune)
        ▼
     [ 磁盘物理删除 ] (不可恢复)
```

通过学习接下来的两个章节，您将掌握完整的灾难抢救流程，以及如何精细化定制垃圾回收策略以在安全与存储性能之间取得最佳平衡。
