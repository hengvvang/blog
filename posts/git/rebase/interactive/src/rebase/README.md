# 交互式变基

在厘清了合并与变基的底层原理后，我们进入交互式变基的实战领域。如果说普通的 `git rebase` 是一次自动的历史重放，那么交互式变基（`git rebase -i`）就是给开发者一把精密的“手术刀”，允许我们在重放过程中暂停、干预并重构每一次提交。

## 1. 交互式变基 Todo 文件

交互式变基的核心在于 **Todo 文件（代办单）**。当你启动交互式变基时，Git 会为你生成一个以时间顺序（从旧到新）排列的提交清单，并在每个提交前附带一个动作命令。
这实际上是一个**历史构建脚本**，你可以通过编辑该脚本来控制 Git 重新构造提交历史的每一步。

---

## 2. 核心操作指令：重塑分支的魔法

在 Todo 文件中，你可以通过将 `pick` 替换为其他动作关键字，来指示 Git 在处理该提交时的具体行为：
- **`pick`**：保留并应用当前提交，不作任何改变。
- **`reword`**：应用当前提交的变更，但暂停以允许修改 Commit Message（提交日志）。
- **`edit`**：暂停变基，允许你修改当前提交的代码内容、添加/删除文件，甚至将其拆分为多个更小的提交。
- **`squash`**：将当前提交的修改并入上一个提交中，并将两者的 Commit Message 合并，允许你重新编辑。
- **`fixup`**：将当前提交的修改并入上一个提交，但静默丢弃当前提交的 Commit Message。
- **`drop`**：彻底删除该提交及其包含的所有代码变更。

---

## 3. 变基冲突与逐个解决机制

变基是将提交**逐个应用**在新的基底上，因此它和普通的 Merge 冲突处理存在核心差异：
- **逐个应用，逐个冲突**：如果变基重放的多个提交都涉及到了同一处代码冲突，你需要依次解决这几次提交中的冲突。
- **HEAD 指向反转**：在变基冲突中，`HEAD` 指向的是**当前的变基基底**（即目标分支最新的提交），而 `>>>>>>>` 冲突标记指向的是**你正在应用的那个提交**。这与普通的 `git merge` 刚好相反。
- **控制指令**：使用 `git add` 暂存解决后的冲突，然后运行 `git rebase --continue` 推进，或者在失控时通过 `git rebase --abort` 安全撤销。

---

## 4. 自动变基与清理流 (Auto-squashing)

为了提高历史整理的效率，Git 提供了自动变基（Auto-squash）流：
1. 本地调试或修复时，使用 `git commit --fixup <commit-hash>` 创建一个特定前缀的提交。
2. 随后执行 `git rebase -i --autosquash <base>`，Git 会在生成的 Todo 清单中，自动将该 fixup 提交移动到目标提交下方，并将操作码改为 `fixup`。
3. 保存并退出后，Git 即可静默完成历史合并，无需任何手动交互，是极具生产力的开发模式。
