# 前言：Zephyr 内存与线程调试的艺术

在嵌入式与物联网（IoT）开发中，微控制器（MCU）如 ARM Cortex-M、ESP32 或 RISC-V 架构通常只拥有极其有限的 SRAM 资源。在如此受限的硬件之上运行实时操作系统（RTOS）时，**内存安全与系统稳定性**是决定产品能否达到工业级品质的关键。而在所有内存问题中，最隐蔽、最难以复现且排查成本最高的，莫过于**线程栈溢出（Stack Overflow）**和**动态堆泄漏（Heap Leak）**。

Zephyr RTOS 作为现代化的、面向安全关键性（Safety-Critical）应用设计的 RTOS，内置了一套极具工业水准的调试工具链与内核保护机制。本指南致力于深度剖析 Zephyr 内部的线程栈分析器（Thread Stack Analyzer）、软硬件栈保护（MPU/Canary/PSPLIM）以及系统/用户堆内存泄漏诊断机制，帮助工程师构建从“实时监控”到“事后诊断”的完整闭环调试体系。

## Zephyr SRAM 物理与逻辑内存布局

为了在底层理清栈与堆的边界，以下架构图展示了典型 Zephyr 固件在 SRAM 中的物理分布，以及硬件内存保护单元（MPU）和软件哨兵（Sentinel）的作用位置：

```text
+-------------------------------------------------------------+  SRAM 高地址 (0x200XXXXX)
|                  主栈 (Main Stack / MSP)                    |  <- 中断服务程序 (ISR) 共享
+-------------------------------------------------------------+
|                                                             |
|                      系统堆 (System Heap)                    |  <- k_malloc/k_free 作用区
|                                                             |
+-------------------------------------------------------------+
|                                                             |
|                       用户堆 (User Heaps)                    |  <- sys_heap / k_heap 隔离区
|                                                             |
+-------------------------------------------------------------+
|  线程 A 栈 (Thread A Stack / PSP)                            |
|  +-------------------------------------------------------+  |
|  | [栈顶] (Stack Base / 递减增长起点)                     |  |
|  | ..................................................... |  |
|  | 活动栈帧 (Active Frames)                              |  |
|  | 历史脏区 (Dirty Area / 曾经的最高水位)                |  |  <- 栈分析器扫描边界
|  | 0xAA 填充未用区 (Unused Area)                         |  |
|  | 栈底哨兵 (Sentinel / Canary 4-Byte: 0xDEADBEEF)       |  |  <- 软件栈溢出检测点
|  | [栈限制] (Stack Limit / 物理终止线)                   |  |
|  +-------------------------------------------------------+  |
|  | MPU 警戒区 (MPU Guard / No Access)                    |  |  <- 硬件栈溢出拦截页
+--+-------------------------------------------------------+--+
|  线程 B 栈 (Thread B Stack / PSP)                            |
|  +-------------------------------------------------------+  |
|  | [栈顶] (Stack Base)                                    |  |
|  | ..................................................... |  |
|  | [栈限制] (Stack Limit)                                |  |
|  +-------------------------------------------------------+  |
|  | MPU 警戒区 (MPU Guard / No Access)                    |  |
+-------------------------------------------------------------+  SRAM 低地址 (0x20000000)
```

如上图所示，Zephyr 的内存管理呈现以下核心特征：
1. **栈与中断隔离**：所有的线程任务在独立分配的线程栈中运行，使用进程栈指针（PSP）；而所有的中断服务程序（ISR）均共享系统的主栈（MSP）。这极大地减轻了单个线程的栈开销压力。
2. **多重栈防御**：结合了基于硬件 MPU（内存保护单元）的强行拦截（Guard Region）与基于软件 Canary（金丝雀字节）的定期巡检。
3. **隔离堆管理**：全局系统堆与模块化用户堆物理分立，避免单个网络驱动或高层业务的堆泄漏耗尽全局资源。

## 本书内容与章节路线图

本指南分为两个核心部分，共包含三个深度技术章节，章节之间层层递进：

### 第一部分：线程栈分析器原理与使用
*   **[线程栈分析器介绍](analyzer/README.md)**  
    本篇概括性介绍线程栈的分配哲学、水位线（Watermark）监控的必要性，以及 Zephyr 中如何通过特定的软件机制追踪物理内存分配。
*   **[第一章：配置、启用与运行时栈水位线分析](analyzer/thread-stack-analyzer.md)**  
    深度讲解 Thread Stack Analyzer 的底层估算算法（`0xAA` 模式匹配）、Kconfig 编译选项优化、后台自扫描线程（Daemon Thread）的生产级 C 代码实现，以及在 Shell 交互环境下的数据多维度解读。

### 第二部分：栈溢出检测与内存泄漏调试
*   **[调试与安全保护介绍](debugging/README.md)**  
    本篇概述在资源受限系统中的防线设计，包括硬件 MPU、软件哨兵机制以及动态堆内存管理的底层挑战。
*   **[第二章：栈高水位计算与 MPU 硬件保护机制](debugging/kernel-watermark-checks.md)**  
    深入探讨 `CONFIG_HW_STACK_PROTECTION` 和 `CONFIG_STACK_SENTINEL` 的物理本质。针对 ARM Cortex-M 架构，详细解剖在硬故障（HardFault）发生时，如何读取 `CFSR`、`MMFAR`、`PSP/MSP` 寄存器，并结合 ELF 文件及符号表快速回溯崩溃源。
*   **[第三章：系统堆内存泄漏诊断与定位流程](debugging/memory-leak-diagnosis.md)**  
    聚焦于系统堆与用户堆的运行状态监控。展示如何利用 `CONFIG_SYS_HEAP_RUNTIME_STATS` 实时监测可用字节，并手把手编写一套生产级的堆分配追踪器（Heap Tracker），通过宏重定向和链接器包裹（Wrapper），在不破坏业务逻辑的前提下捕获恶意未释放的内存块。

## 预期学习目标

通过对本书的系统学习与实践，您将掌握以下核心能力：
1. **精密栈预算控制**：告别“凭感觉分栈大小”的粗放开发，学会根据运行时高水位数据进行科学的栈裁剪，释放 RAM 冗余。
2. **零时延硬故障捕获**：在产品发生 crash 时，通过提取寄存器快照和 MPU 状态字，在秒级时间内判定“是否是栈溢出导致的 HardFault”，并逆向定位到具体的出错代码行。
3. **自研内存监测链**：能在不需要昂贵硬件 Trace 仿真器的环境下，通过定制化的 Heap Alloc Tracker 追踪任意内存泄漏源，并设计设备侧的异常自愈机制。
